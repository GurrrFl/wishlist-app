# Процесс создания диаграммы классов (UML)

## 1. Введение и цель

Этот документ описывает теоретические основания и последовательность действий при создании подробной диаграммы классов для проекта "Wishlist App". Диаграмма отражает статическую структуру системы и используется как основное средство Logical View по подходу Rational Unified Process (RUP).

## 2. Краткая теория (основные положения)

- Диаграмма классов — граф, вершины которого — классификаторы (классы, интерфейсы), рёбра — структурные отношения (ассоциации, агрегация, композиция, наследование, зависимости).
- Основные элементы: класс (имя, атрибуты, операции), интерфейс (реализация классами), абстрактные классы, стереотипы и ассоциации с кратностью.
- Типы связей:
  - Ассоциация: обычная связь между экземплярами классов; может иметь имя и кратности.
  - Агрегация (неполная принадлежность): `o--` в PlantUML (слабая связь).
  - Композиция (сильная принадлежность): `*--` (жёсткая, часть не существует без целого).
  - Наследование / реализация: `<|--` / `..|>`.
  - Зависимость: `..>` (использование типа или вызов методов).

## 3. Связь диаграммы с представлениями RUP

- Use Case View: задаёт требования — какие сценарии покрывает система (не детализируется на диаграмме классов, но влияет на её структуру).
- Logical View: диаграмма классов — ключевой артефакт, формирует модель предметной области.
- Component View: показывает реализацию — репозитории, сервисы, интерфейсы и их зависимости (в диаграмме выделены стереотипы `<<repository>>`, `<<service>>`).
- Deployment View: не входило в задачу; при необходимости указываются инфраструктурные классы (например, `EmailNotifier`).

## 4. Этапы работы (ход выполнения)

1. Анализ кода и требований
   - Просмотреть модели (ORM), репозитории, сервисы и маршруты.
   - Выделить основные сущности предметной области (в нашем случае: `User`, `Wishlist`, `Gift`, `Reservation`).

2. Определение уровня детализации
   - На раннем этапе — только имена классов и основные связи.
   - Подробный вариант — атрибуты, ключевые операции, интерфейсы и стереотипы.

3. Выделение вспомогательных компонентов
   - Добавить репозитории, сервисы и интерфейсы, отражающие архитектуру приложения (Component View).

4. Проектирование связей
   - Указать кратности: `User 1..* Wishlist`, `Wishlist 1 *-- 0..* Gift` и т.д.
   - Выбрать композицию или агрегацию, исходя из семантики владения.

5. Формализация в нотации UML (PlantUML)
   - Использовать PlantUML для удобного текстового описания диаграммы и последующего рендеринга.
   - Добавить стереотипы, интерфейсы и заметки для пояснений.

6. Проверка и итерация
   - Сопоставить диаграмму с реальными классами проекта и скорректировать.

## 5. Применение к проекту "Wishlist App"

- Основные доменные классы: `User`, `Wishlist`, `Gift`, `Reservation`.
- Служебные классы и интерфейсы: `IAuthService`, `INotifier`, `AuthService`, `EmailNotifier`.
- Репозитории представлены как реализации абстрактного `BaseRepository<T>` и помечены стереотипом `<<repository>>`.
- Ассоциации:
  - `User` агрегирует `Wishlist` (пользователь владеет набором списков желаний).
  - `Wishlist` композиционно содержит `Gift` (подарки принадлежат конкретному списку).
  - `Reservation` связывает `User` и `Gift` и отражает кратности и историю бронирования.

## 6. Технические шаги для рендеринга (PlantUML)

1. Установите PlantUML и Java (если нужно локально) или используйте онлайн-рендерер.
2. Файл диаграммы: `docs/class_diagram_detailed.puml`.
3. Команда для локального рендеринга (в корне backend):

```bash
plantuml docs/class_diagram_detailed.puml
```

Это создаст `class_diagram_detailed.png` в той же папке.

## 7. Советы по дальнейшему использованию

- Для документации проекта добавьте сгенерированные изображения в `README.md` или Confluence.
- Поддерживайте диаграммы в актуальном состоянии при изменениях моделей.
- Создавайте несколько диаграмм классов с разной степенью детализации (high-level и detailed).
